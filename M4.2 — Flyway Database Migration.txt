# M4.2 — Flyway Database Migration

You are a Senior Database Engineer specializing in PostgreSQL, Flyway, Spring Boot, and database schema management.

We are implementing the approved database design for the Mini Workshop Booking System.

## 1. Source documents

Read these documents first:

- `docs/requirements.md`
- `docs/architecture.md`
- `docs/database-design.md`
- `docs/api-specification.md`

The approved `docs/database-design.md` is the authoritative source for the database schema.

Do not invent or silently change database columns, relationships, constraints, or business rules.

## 2. Inspect the existing project

Before making changes:

- Inspect `backend/pom.xml`.
- Inspect existing Spring Boot configuration.
- Inspect existing database folders and migration files.
- Check Git status.
- Check whether the PostgreSQL database `workshop_booking_db` exists.
- Identify any existing database schema or data that could be affected.

Do not overwrite existing migrations or database data.

If M4.1 is incomplete or the backend project does not exist, report the issue before proceeding.

## 3. Add Flyway dependencies

Configure Flyway in the Spring Boot Maven project.

Use Spring Boot dependency management for compatible Flyway versions.

Include the required PostgreSQL database support.

Do not add unnecessary dependencies.

## 4. Create the initial migration

Create:

`backend/src/main/resources/db/migration/V1__create_initial_schema.sql`

Implement the approved schema for:

1. `accounts`
2. `workshops`
3. `registrations`
4. `email_outbox`

Include all approved:

- Columns and PostgreSQL data types.
- Primary keys.
- Foreign keys.
- Unique constraints.
- NOT NULL constraints.
- CHECK constraints.
- Default values.
- Indexes.
- Restrictive foreign key deletion behavior.

Use:

`BIGINT GENERATED BY DEFAULT AS IDENTITY`

for approved identity primary keys.

Implement the approved email normalization and uniqueness design consistently.

Respect the approved design decisions:

- Workshop status is derived and is not stored as a column.
- Workshop timestamps use `TIMESTAMPTZ`.
- The application uses `Asia/Phnom_Penh`.
- Registration and its email outbox record must be capable of being created in one transaction.
- One successful registration has one outbox record.
- Failed outbox records are retained.
- Capacity and duplicate registration integrity must be supported by the approved constraints and transaction design.

Do not introduce database triggers for Instructor-role assignment.

## 5. Configure Flyway

Configure Spring Boot to:

- Discover migrations automatically.
- Validate migration checksums.
- Apply pending migrations.
- Fail startup when migration validation fails.

Use Flyway as the schema migration authority.

Disable Hibernate schema creation/update. Configure Hibernate to validate the schema rather than create or modify it.

Keep database credentials outside source control.

## 6. Database connection configuration

Use the approved database name:

`workshop_booking_db`

Provide environment-based configuration examples.

Do not hardcode real passwords.

Do not automatically create or drop an existing database.

Do not connect to a production database.

## 7. Migration verification

If a dedicated local development database is available and confirmed safe to use:

1. Apply the V1 migration.
2. Verify all four tables exist.
3. Verify primary and foreign keys.
4. Verify unique and CHECK constraints.
5. Verify indexes.
6. Verify Flyway migration history.

If the database is unavailable or cannot be confirmed safe, do not execute the migration. Report the exact manual verification steps instead.

Do not drop existing tables or data.

## 8. Testing

Add appropriate migration verification tests if the existing project supports them.

Prefer PostgreSQL integration testing with Testcontainers where appropriate.

Do not rely only on H2 for PostgreSQL-specific behavior.

## 9. Restrictions

- Do not modify approved SDD documents.
- Do not create Java entities or repositories.
- Do not implement business services.
- Do not implement REST APIs.
- Do not create additional application features.
- Do not add unapproved database columns or tables.
- Do not modify existing migration history.
- Do not execute destructive SQL.
- Do not commit or push.

Report:

1. Flyway dependencies added.
2. Migration files created.
3. Tables and constraints implemented.
4. PostgreSQL configuration.
5. Hibernate configuration.
6. Migration execution result.
