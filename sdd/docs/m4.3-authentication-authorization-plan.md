# M4.3 — Authentication and Authorization Implementation Plan

| Document information | Value |
|---|---|
| Project | Mini Workshop Booking System |
| Document | M4.3 Authentication and Authorization Implementation Plan |
| Status | Planning only; owner decisions incorporated |
| Scope | Backend authentication, authorization, CSRF, sessions, and React integration |

## 1. Purpose and boundaries

This plan describes implementation of the approved Admin and Instructor authentication and authorization behavior. It follows the approved requirements, architecture, database design, API specification, and project instructions.

This plan does not authorize changes to those specifications. It adds no public staff registration, password reset, session database table, token endpoint, separate-origin CORS configuration, or new product feature. Implementation will use the existing single Spring Boot application and the approved `accounts` table.

## 2. Version verification for Spring Security SPA CSRF

The backend `pom.xml` uses the Spring Boot parent `3.5.16`, includes `spring-boot-starter-security`, and does not declare a Spring Security version override or a direct version pin. Spring Boot 3.5.16 manages Spring Security artifacts at **6.5.11**, including `spring-security-web` and `spring-security-config`, according to its [managed dependency coordinates](https://docs.spring.io/spring-boot/3.5/appendix/dependency-versions/coordinates.html).

The project will use the Spring Security **6.5** servlet SPA CSRF API pattern: `CookieCsrfTokenRepository`, a custom `CsrfTokenRequestHandler` combining `CsrfTokenRequestAttributeHandler` and `XorCsrfTokenRequestAttributeHandler`, and the cookie customization APIs available in this version. The [Spring Security 6.5 SPA CSRF reference](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html) documents the raw-cookie header handling, deferred token loading, BREACH behavior, and cookie clearing after authentication and logout. The [6.5 CookieCsrfTokenRepository API](https://docs.spring.io/spring-security/site/docs/6.5.x/api/org/springframework/security/web/csrf/CookieCsrfTokenRepository.html) documents cookie name, header name, path, and cookie customization APIs.

Before implementation, confirm the actual resolved dependency with Maven dependency inspection if the POM, parent, profiles, or dependency management has changed. Do not choose a CSRF API based only on current/Spring Security 7 documentation.

## 3. Authentication and session architecture

### 3.1 Spring Security responsibilities

Configure one Spring Security filter chain for the existing `/api/v1` REST API:

- Permit documented public workshop list/detail and visitor registration routes, plus `POST /api/v1/auth/login`.
- Require authentication for `GET /api/v1/auth/me` and `POST /api/v1/auth/logout`.
- Require `ADMIN` for documented Admin routes.
- Require `INSTRUCTOR` for documented Instructor routes.
- Keep CSRF enabled for all state-changing requests, including login, logout, visitor registration, and Admin writes.
- Return the approved JSON error contract: `401` for unauthenticated or invalid login, `403` for insufficient role or CSRF rejection, and the documented codes/messages without internal details.

Do not use frontend route guards as the authorization boundary. Do not expose password hashes or security internals in API responses.

### 3.2 Account lookup and login behavior

Use the existing `accounts` table and Spring Security authentication support. Normalize login email by trimming and lowercasing with Java `Locale.ROOT`, matching the finalized database design. Reject accounts with `active = false`. Unknown email, incorrect password, and inactive accounts must produce the same `401 INVALID_CREDENTIALS` response so the API does not disclose which condition failed.

Implement only the approved authentication routes:

| Endpoint | Required behavior |
|---|---|
| `POST /api/v1/auth/login` | Validate credentials and account activity; establish an authenticated server-side session; return account ID, email, display name, and role; issue the session cookie only through `Set-Cookie`. Require the CSRF header. |
| `GET /api/v1/auth/me` | Return the current authenticated account and role. Do not accept identity or role from the client. |
| `POST /api/v1/auth/logout` | Require authentication and CSRF; invalidate the current session immediately; expire the session cookie; return the API-specified `204 No Content`. |

Retain Spring Security session-fixation protection when authentication succeeds.

### 3.3 Server-side session and session cookie

Use the servlet container's server-side HTTP session for this single-instance demonstration project. Do not add a database session table, Redis, or another session service. Configure a **30-minute inactivity timeout**; normal activity refreshes the inactivity period. Successful logout invalidates the session immediately.

Session cookie policy:

- `HttpOnly=true`
- `SameSite=Lax`
- Development over HTTP: `Secure=false`
- Production over HTTPS: `Secure=true`

Keep session identifiers out of JSON, React state, browser local storage, logs, and URLs.

## 4. SPA CSRF configuration and lifecycle

### 4.1 Cookie repository

Configure Spring Security's servlet `CookieCsrfTokenRepository` with:

- Cookie name: `XSRF-TOKEN`
- Request header: `X-XSRF-TOKEN`
- Cookie path: `/`
- CSRF cookie `HttpOnly=false`, so React can read it
- `SameSite=Lax`
- Development over HTTP: `Secure=false`
- Production over HTTPS: `Secure=true`

These attributes apply to the CSRF cookie; the session cookie remains `HttpOnly=true`. Do not treat the readable CSRF token as an authentication credential. Use the Spring Security 6.5 cookie customization API for cookie attributes and avoid deprecated setters when the 6.5 API provides a customizer.

### 4.2 SPA-compatible request handling and BREACH protection

Use a custom `CsrfTokenRequestHandler` compatible with the Spring Security 6 SPA pattern:

1. Use `XorCsrfTokenRequestAttributeHandler` to expose the token with Spring Security's BREACH protection behavior.
2. When the approved `X-XSRF-TOKEN` header is present, resolve its raw cookie token value with `CsrfTokenRequestAttributeHandler`; React sends the raw value read from `XSRF-TOKEN`.
3. Preserve XOR-based handling for request parameters or other token representations where applicable.
4. Do not disable BREACH protection to make raw cookie/header matching work.

The repository and handler must agree on the cookie/header names. The request handler must also account for Spring Security's deferred `CsrfToken` loading: the handler must force the deferred token to load when necessary so the repository writes a cookie.

### 4.3 Initial token and post-authentication/logout refresh

No CSRF token endpoint will be added. An existing safe API request, such as `GET /api/v1/workshops`, must cause the deferred token to load and return `Set-Cookie: XSRF-TOKEN=...; Path=/...` when a token is absent. The Vite proxy forwards this request to the backend while the browser continues to use the same-site `/api/v1` path.

Spring Security clears the CSRF cookie after successful authentication and logout. To return a fresh token on each of those responses:

- After successful login, the authentication success path must generate a new token and save it through the configured repository **after** Spring Security's authentication CSRF-clearing behavior has run.
- After successful logout, the logout success path must generate a new token and save it through the configured repository **after** the logout CSRF-clearing handler has run.
- The response must contain the fresh `XSRF-TOKEN` cookie, not only an expired-cookie instruction. React reads that refreshed cookie before its next state-changing request.
- Do not rely on a cached deferred token from before the clear operation. Generate a new token after the clear, then save it to the response.

This uses existing login/logout responses and existing public safe API requests; it does not add an endpoint or change the JSON response contract. The 6.5 SPA handler pattern and cookie refresh behavior are grounded in the [official 6.5 CSRF reference](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html).

### 4.4 Same-site development and production deployment

- Spring Boot listens on port `8181` during development.
- React uses the Vite development proxy so application requests use the relative `/api/v1` path.
- Development cookies use `Secure=false` for local HTTP; production uses HTTPS and `Secure=true`.
- The approved setup is same-site; do not add separate-origin CORS configuration for this flow.

## 5. Authorization and Instructor ownership

Enforce route-level roles in Spring Security and ownership in backend service/query logic:

- **Visitor/unauthenticated:** documented public workshop reads and visitor registration only; no staff or participant data.
- **Admin:** all documented Admin workshop operations and participant listings for any workshop.
- **Instructor:** only assigned workshops and participants for those workshops; no workshop management or registration changes.

For every Instructor request, derive the account ID from the authenticated session. Filter workshop and participant queries by that account's assignment. Never trust a client-supplied account ID, role, or instructor ID as proof of access. Follow the API's documented `403` behavior for authenticated callers with insufficient permission and `401` for unauthenticated callers.

## 6. Password hashing and secure initial Admin provisioning

Use `BCryptPasswordEncoder` with strength **12** for staff password hashes. Store only the encoded output in `accounts.password_hash`. Never persist or log a plaintext password; do not echo credentials in command output or errors. Do not add a password reset flow, which is excluded from Version 1.

Provide a dedicated, one-time operator command for initial Admin provisioning:

- Read Admin email, display name, and password from environment variables, never command-line arguments or source-controlled files.
- Require all inputs and reject invalid or blank values before persistence.
- Normalize the email as specified by the database design.
- Hash the password with `BCryptPasswordEncoder` strength 12.
- Create an `ADMIN` account only when no Admin already exists.
- Refuse to overwrite an existing Admin and fail if the email is already used by any account.
- Create no public Admin registration endpoint and use no default credentials.
- Run transactionally, emit no secrets in logs, and exit clearly with success/failure status.

The exact environment-variable names and command invocation are implementation details not specified by the approved product documents; choose clear names and document the operator procedure as part of implementation without changing product behavior.

## 7. React integration workflow

The React API client will:

1. Call a safe existing API route through `/api/v1` on application initialization to obtain the CSRF cookie.
2. Read the `XSRF-TOKEN` cookie and add its raw value in the `X-XSRF-TOKEN` header for every state-changing request.
3. Use browser-managed session cookies; never copy the session ID into application storage.
4. After successful login, read the refreshed `XSRF-TOKEN` cookie before the first authenticated write.
5. After logout, read the freshly returned CSRF cookie before a later login.

The Vite proxy keeps development requests same-site and avoids separate-origin CORS configuration. Frontend checks complement, but do not replace, backend authorization and CSRF enforcement.

## 8. End-to-end CSRF verification sequence

Verify the complete browser/API flow with a real HTTP session and cookie jar. Do not put real credentials in test output.

1. **Initial safe GET:** issue `GET /api/v1/workshops` through the Vite proxy without an `XSRF-TOKEN`; verify a successful public response and a newly generated `XSRF-TOKEN` cookie with `Path=/`, `HttpOnly=false`, `SameSite=Lax`, and the environment-appropriate `Secure` attribute.
2. **Login:** read the raw cookie value and send it in `X-XSRF-TOKEN` on `POST /api/v1/auth/login`; verify successful authentication, session cookie flags, no session ID in JSON, and a fresh CSRF cookie in the response after Spring Security clears the previous token.
3. **Authenticated write:** use the refreshed cookie value in the header on an approved Admin state-changing request; verify success for an Admin session. Verify the stale pre-login token fails.
4. **Logout:** send `POST /api/v1/auth/logout` with the current CSRF cookie value in the header; verify `204`, immediate session invalidation, expired session cookie, and a fresh CSRF cookie after the logout clear operation.
5. **Next login:** use the new CSRF cookie from logout (or, if absent because the cookie was cleared by the browser, first perform the existing safe GET); verify the next login succeeds with the new token and that the old token is rejected.
6. Repeat cookie-attribute checks for development HTTP and production HTTPS configuration without using production credentials.

## 9. Testing strategy

### Unit tests

- Email normalization and account lookup behavior.
- BCrypt hash creation/matching and no plaintext persistence/logging.
- Inactive-account rejection and generic invalid-credential behavior.
- Initial Admin command validation, existing-Admin refusal, email collision refusal, and idempotent non-overwrite behavior.
- Instructor ownership query/service restrictions.

### Spring Security and HTTP integration tests

- Login, `/auth/me`, logout, session rotation/fixation protection, and immediate session invalidation.
- `401`/`403` route matrix for unauthenticated, Admin, and Instructor roles.
- Missing, malformed, stale, and valid CSRF header behavior.
- Cookie name, header name, path `/`, CSRF readability, session `HttpOnly`, `SameSite=Lax`, and dev/prod `Secure` flags.
- Initial safe GET materializes the deferred token cookie.
- Authentication and logout responses each return a fresh token after the old token is cleared.
- Full end-to-end sequence in Section 8, including the post-login state-changing call and next-login token refresh.
- Ensure CSRF response handling preserves Spring Security's XOR/BREACH behavior while accepting the raw token only from the configured header.

Use JUnit 5, Spring Security Test, MockMvc for filter-chain behavior, and PostgreSQL-backed integration tests for persisted accounts and bootstrap behavior. Use test-only accounts and passwords. Report Testcontainers skips accurately; do not claim tests passed unless executed.

## 11. Risks and controls

| Risk | Control |
|---|---|
| React sends a raw cookie token while default BREACH handling expects a masked value | Use the Spring Security 6.5 SPA handler pattern: XOR handler for BREACH-protected request attributes and plain handler for the configured raw header. |
| Deferred token means an initial safe request returns no CSRF cookie | Force token materialization in the approved SPA request handler and verify `GET /api/v1/workshops` returns the cookie. |
| Authentication/logout clears the CSRF cookie | Generate and save a fresh token after each clear in the respective success path; verify response `Set-Cookie` and subsequent requests. |
| Session cookie is exposed to JavaScript | Keep session cookie `HttpOnly=true`; only the CSRF cookie is readable. Never store session IDs in frontend storage. |
| Wrong cookie security flags for local/prod | Verify environment-specific `Secure` values, `SameSite=Lax`, and path `/` for the CSRF cookie. |
| Instructor data leaks through a client-controlled identifier | Derive account from session and scope backend queries by assignment. |
| Initial Admin command leaks or overwrites credentials/account | Use environment variables, BCrypt 12, no credential output, fail if Admin exists, and no public registration route. |
